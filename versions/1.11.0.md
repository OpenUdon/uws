# Udon Workflow Specification v1.11.0

## Version 1.11.0

This document defines the Udon Workflow Specification (UWS) 1.11.0.

The key words `MUST`, `MUST NOT`, `REQUIRED`, `SHALL`, `SHALL NOT`, `SHOULD`, `SHOULD NOT`, `RECOMMENDED`, `NOT RECOMMENDED`, `MAY`, and `OPTIONAL` in this document are to be interpreted as described in BCP 14 when, and only when, they appear in all capitals.

The JSON Schema for UWS 1.11 documents is identified by:

```text
https://github.com/OpenUdon/uws/versions/1.11.0.json
```

This identifier is the schema `$id`. Implementations MAY resolve it by fetching the `versions/1.11.0.json` file from the UWS repository.

## What is the UWS Specification?

The UWS Specification defines a compact workflow overlay for source-backed API and event operations. It describes operation bindings, request values, dependencies, structural control flow, execution semantics, triggers, and runtime expression fields needed by workflow tooling while leaving API, event, and protocol details in the referenced source document.

## Status of This Document

This document describes UWS 1.11.0. Conformance is defined by the normative requirements in this document and by the JSON Schema identified above.

## 1. UWS Specification

### 1.1 Version 1.11.0

The `uws` field identifies the UWS version used by a UWS document. Its lexical form MUST match:

```text
^1\.\d+\.\d+(-.+)?$
```

Examples of published versions include `1.0.0`, `1.1.1`, `1.10.0`, and `1.11.0`. A lexically matching value is not by itself supported: validation and execution MUST require an exact published UWS core version and its matching schema. This distribution publishes no prerelease schemas; values such as `1.0.0-beta.1`, unpublished patch versions, and future versions MUST fail closed. The latest schema MUST NOT be used as a fallback for any other declared version. This exact-version admission rule is a deliberate validator correction that applies to every declared version, including older documents; it does not apply later feature semantics retroactively (see `versions/CHANGELOG.md`).

Patch versions address corrections and clarifications for the 1.x feature set.

## 2. Introduction

UWS defines a language-agnostic workflow document for orchestrating operations described by referenced API and event source documents, plus extension-owned leaf operations declared through implementation profiles.

UWS is intentionally not a replacement for API, RPC, and event description formats such as OpenAPI, Google Discovery, AWS Smithy, AsyncAPI, GraphQL, OpenRPC, Protocol Buffers, or OData. The source document owns HTTP methods, paths, channels, messages, payload schemas, RPC methods, services, metadata, servers, protocol details, and security schemes. UWS owns the workflow overlay and execution model: operation binding, sequencing, request value binding, structural control flow, dependency and trigger semantics, result extraction, runtime expression fields, and dispatch to a bound runtime.

UWS is also distinct from full client-side workflow specifications such as Arazzo and from infrastructure-as-code engines such as OpenTofu and Terraform. Arazzo describes full client-side action sequences and treats each step as a bespoke client action. OpenTofu and Terraform act as full client-side workflow engines for infrastructure: every resource and provider call is described in the client configuration and resolved against a provider plugin at apply time. None of these approaches assume that the underlying operations are already defined by a server contract. UWS takes the opposite position: server actions are pre-defined by the source document, and UWS workflows reference those operations by ID rather than re-describing them. As a result, UWS is a much smaller overlay — it does not duplicate request/response shapes, does not redeclare endpoints, and does not encode anything the source document already specifies.

UWS documents serve as an interchange format for workflow tooling. The specification defines the document model and execution semantics, but does not require a particular executor, implementation, or runtime.

UWS 1.9.1 added an optional `contentTrust` registry for reviewed integrity provenance and a deterministic advisory analysis contract. The registry does not change operation, workflow, or step output shapes. Analysis findings do not enter ordinary validation, prevent execution, or alter executor results.

UWS 1.10.0 published a portable execution contract for expression truthiness, pointer criteria, delay and polling behavior, executable entry selection, structural result records, actions, trigger dispatch, and security responsibilities. UWS 1.11.0 preserves the UWS 1.x wire model and adds version-gated expression forms, numeric delay and batch-size literals, root-scoped terminal `goto`, and corrected `forEach` merge record selection. Except for the explicit exact-version admission correction and other documented cross-version bug fixes, later feature semantics do not apply to earlier declarations.

A UWS document is a JSON-compatible object model. Expression fields are strings. Structured bodies such as `request`, `variables`, and trigger `options` use JSON-compatible values so they can be represented consistently in the supported serializations described by §4.1.

### 2.1 Scope

The UWS core workflow contract remains narrow. UWS focuses on API and event source operation binding, workflow structure, request value binding, structural execution semantics, result extraction, trigger dispatch, and runtime expression fields.

UWS core does NOT define:

- A reusable-component registry for criteria, success actions, or failure actions. Criteria and actions are declared inline on the operation or workflow that uses them. Cross-operation reuse is expressed through implementation profiles or by duplicating the declaration.
- A separate Parameter object or a Reusable Object (`{reference, value}`). Request values are carried by the Request Binding Object (§4.5.5) whose keys map to common source request locations (`path`, `query`, `header`, `cookie`, `body`).
- A payload-replacement model for request bodies. The body value is bound directly under `request.body`.
- Runtime auth, provider configuration, protocol serialization details, credentials, and request/response schemas. These remain source-derived, executor-owned, or extension-owned.
- Credential storage, idempotency storage, or retry replay protection backends. Workflow idempotency metadata is portable orchestration intent; persistence and enforcement are executor responsibilities.

Reuse of runtime behavior is delegated to the referenced source document (for source-bound API or event operations) and to implementation profiles (for extension-owned operations).

## 3. Definitions

### 3.1 UWS Document

A self-contained workflow document conforming to this specification.

### 3.2 Source Description

An API or event description document referenced by operations in a UWS document.

### 3.3 Operation

A UWS-local executable unit bound to one operation in a referenced API or event source document, or an extension-owned operation identified by an implementation profile.

### 3.4 Workflow

A structural control-flow construct that composes operations or nested steps into sequence, parallel, switch, merge, loop, or await patterns.

### 3.5 Step

A unit inside a workflow. A step has exactly one execution form: it references an operation through `operationRef`, invokes a workflow through `workflow`, or declares a structural construct through `type`. The first two forms MUST NOT also declare structural child blocks. The `type` form defines its behavior and children according to §4.5.6.3.

### 3.6 Trigger

An entry point that initiates workflow execution, such as a webhook endpoint.

### 3.7 Runtime Expression

A string expression evaluated at execution time, used for conditional logic (`when`), iteration (`forEach`), waits (`wait`), outputs (`outputs`), and success criteria (`successCriteria`). Workflow-reference fields contain literal workflow IDs.

### 3.8 Specification Extension

A custom field prefixed with `x-`. Extension fields are preserved by compliant tooling but are not interpreted by the UWS core specification.

### 3.9 Orchestrator

The UWS core component that manages workflow state transitions and structural control flow according to the specification.

### 3.10 Implementation Profile

An implementation-specific profile that defines how an extension-owned operation or extension expression feature is executed or evaluated.

### 3.11 Content Trust

Reviewed integrity provenance describing whether runtime content is `trusted`, `untrusted`, or of `unknown` provenance. Content trust is distinct from confidentiality and from the value capability described in §4.7.2.

## 4. Specification

### 4.1 Format

A UWS document is a JSON object. It MAY be represented as JSON, YAML, or canonical HCL.

All field names in the specification are case sensitive unless explicitly noted otherwise.

JSON and YAML documents MAY contain specification extensions. HCL representations MUST preserve specification extensions without changing their names or values. If an HCL tool cannot represent an extension-bearing document without loss, it MUST reject that document rather than silently drop extension fields.

### 4.2 Data Types

Data types in UWS are based on JSON-compatible values and JSON Schema-compatible schema objects.

The following type names are used in this document:

| Type | Meaning |
|---|---|
| `string` | JSON string. |
| `number` | JSON number. |
| `integer` | JSON number without a fraction or exponent part. |
| `boolean` | JSON boolean. |
| `any` | Any JSON-compatible value. |
| `Map[string, any]` | JSON object with string keys. |
| `ParamSchema` | UWS parameter schema object. |
| `[T]` | JSON array of values of type `T`. |

### 4.3 Relative References in URLs

Unless otherwise specified, URL fields MAY use relative references. Relative source description URLs are resolved relative to the containing UWS document. For in-memory documents, the implementation supplies the base directory or base URL.

### 4.4 Relationship To Source Documents

Every executable core operation MUST bind to an API or event source operation through a `sourceDescription` plus exactly one selector. Since UWS 1.2, UWS uses the generic selectors introduced in that release:

- `sourceOperationId`: the source document operation identifier.
- `sourceOperationRef`: a JSON Pointer fragment to an operation in the source document.

For `type: openapi` sources, implementations MUST also accept the backward-compatible selectors:

- `openapiOperationId`: the OpenAPI `operationId`.
- `openapiOperationRef`: a JSON Pointer fragment to an OpenAPI operation when `operationId` is unavailable or unsuitable.

UWS core MUST NOT duplicate method, path, schema, server, security, provider configuration, credential, or protocol serialization data. Tools that need those details derive them from the referenced source document or from extension-owned runtime configuration.

`sourceDescription.type` is authoritative. Missing `type` defaults to `openapi`. For `google-discovery`, `aws-smithy`, `asyncapi`, `graphql`, `openrpc`, `grpc-protobuf`, `odata`, and `browser-profile` sources, operations MUST use one of the generic `sourceOperation*` selectors and MUST NOT use the legacy `openapiOperation*` selectors.

For `type: asyncapi` sources, `sourceOperationId` identifies a root AsyncAPI Operation Object key. `sourceOperationRef` is a JSON Pointer fragment intended to resolve against the AsyncAPI source document. UWS core validators only enforce JSON Pointer fragment syntax; source-aware tooling and runtimes validate whether the pointer resolves to a supported AsyncAPI target. The preferred target is `#/operations/<name>`. Runtimes MAY also accept `#/channels/<name>` and `#/channels/<name>/messages/<name>` as compatibility targets when the operation can be resolved unambiguously. AsyncAPI channels, messages, payload schemas, protocol bindings, servers, and security remain owned by the AsyncAPI document and the bound runtime.

For `type: graphql`, `openrpc`, `grpc-protobuf`, and `odata` sources, UWS core only standardizes the source family name and selector shape. Source-aware tooling and runtimes validate whether a selector resolves to a supported GraphQL operation, JSON-RPC method, gRPC service method, OData entity operation, OData function, or OData action. GraphQL schemas and operation documents, OpenRPC method definitions, protobuf descriptors, and OData CSDL metadata remain source-owned.

For `type: browser-profile` sources, `sourceOperationId` identifies an action key in the profile's `actions` object; `sourceOperationRef`, when used, MUST be a JSON Pointer fragment whose preferred target is `#/actions/<name>`. UWS core validates the JSON Pointer fragment syntax; browser-aware tooling and runtimes validate whether the selector resolves to a supported profile action, enforce the profile's accessibility-first locator vocabulary, restrict UI interactions to the closed declarative macro set, and check origin-allowlist, confirmation, and expiry safety rules. The browser profile sub-spec is published separately, with `versions/browser.1.9.{json,md}` as the current opt-in contract; Browser 1.5–1.8 remain accepted published profiles. UWS core does not duplicate the profile schema, locator vocabulary, action vocabulary, output extraction methods, or safety controls. Browser execution, session contexts, credentials, cookies, and rendering remain runtime-private. By design, `browser-profile` is the weakest first-class source type — tooling SHOULD prefer a published API source when one covers the task (see `docs/future-source-profiles.md` "Browser Profile Scope").

Credential storage, provider defaults, non-HTTP runtimes, and product-specific execution metadata belong in `x-*` extensions or implementation profiles. An operation without a source binding is an extension-owned operation and MUST include `x-uws-operation-profile` with at least one non-whitespace character to name the implementation profile that can execute it.

#### 4.5.3 Source Description Object

The object describes an API or event source document referenced by UWS operations.

HTTP method, path, channel, message, server, request/response schema, payload schema, security information, provider defaults, credential bindings, and protocol serialization details are resolved from the referenced source operation or executor-owned configuration, not from UWS core fields.

`sourceOperationRef` and `openapiOperationRef` are JSON Pointer fragments resolved against the document named by `sourceDescription`. They MUST begin with `#/`. UWS core does not load the referenced source document; resolution of the pointer target is the responsibility of the execution runtime.

If `sourceDescription`, generic selectors, and legacy OpenAPI selectors are all omitted, the operation is extension-owned and MUST include `x-uws-operation-profile`. Extension-owned operations are valid UWS documents but are executable only by implementations that understand the selected extension profile.

| # | Shape | `sourceDescription` | Generic selector | Legacy OpenAPI selector | `x-uws-operation-profile` |
|---|---|---|---|---|---|
| 1 | Source-bound by `sourceOperationId` or `sourceOperationRef` | REQUIRED | Exactly one REQUIRED | MUST NOT be set | OPTIONAL |
| 2 | OpenAPI-bound by `openapiOperationId` or `openapiOperationRef` | REQUIRED to an `openapi` source | MUST NOT be set | Exactly one REQUIRED | OPTIONAL |
| 3 | Extension-owned | MUST NOT be set | MUST NOT be set | MUST NOT be set | REQUIRED |

##### 4.5.4.3 Operation Timeout

`timeout` bounds one operation attempt delegated to the bound runtime. The timeout clock starts when the operation is eligible to start, after its `dependsOn` dependencies have completed and after its `when` condition allows execution. For a retrying operation, each retry attempt receives a fresh timeout budget.

When an operation timeout expires, the operation fails with a timeout failure. Matching `onFailure` actions are evaluated using the same failure handling rules as other operation failures. A parent workflow timeout or context cancellation MAY terminate the operation before its own timeout expires.

##### 4.5.6.3 Workflow Type Semantics

The `type` field selects one of six structural constructs. The following definitions apply to both Workflow objects and Step objects that set `type`.

- **`sequence`** — Steps execute in declaration order. Each step MUST complete before the next begins. `dependsOn` MAY add cross-workflow dependencies that extend the declaration order. `items` MUST NOT be set on a `sequence`.

- **`parallel`** — Steps execute concurrently, subject to `dependsOn` relationships. The first branch error cancels the shared branch context; the construct returns an execution error after branches terminate. A `goto` or `end` control signal from a branch is an error because cross-branch control flow is undefined. `parallelGroup` is a dependency barrier only: a dependency on the group waits for all members in declaration order. `items` MUST NOT be set on a `parallel`.

- **`switch`** — Cases are evaluated in declaration order. The first case whose `when` expression is truthy executes its `steps`; a case without `when` is an unconditional match at its position. No later case executes. If none matches and `default` is present, `default` executes; otherwise the switch completes without executing steps. `items` MUST NOT be set on a `switch`.

- **`loop`** — Iterates over the ordered collection returned by resolving `items`. `items` is REQUIRED. Each item runs the nested `steps` sequentially with `$item` and its zero-based `$index`. A present `batchSize` MUST resolve to a positive integer; it groups sequential iterations and exposes the batch plus zero-based `$batchIndex` to the runtime. In UWS 1.11 and later `$batchIndex` is a grammar-defined expression available only inside this `loop` context. Batching does not authorize concurrent iteration. On success, the loop record result is an array of `{index, batchIndex, item}` objects in source order; empty items produce an empty array. `cases` and `default` MUST NOT be set on a `loop`.

- **`merge`** — Reads execution records for only the constructs named by `dependsOn`; it does not execute nested `steps`, so portable documents SHOULD omit them and MUST NOT rely on them executing. Dependency records appear in `dependsOn` order. A parallel-group dependency expands members in declaration order; repeated dependencies and members are included once. In UWS 1.11 and later, if a `forEach` dependency produced iteration records, the merge includes those records in numeric iteration order and excludes that dependency's parent aggregate record. If there are no iteration records because the `forEach` was skipped or had zero items, the merge includes its parent record once. A dependency that fails still aborts the merge. Each record object contains `id`, `kind`, `status`, `error`, `result`, and `outputs`; `error` is an empty string when there is no error, while unavailable `result` and `outputs` values are null. The merge record result is the ordered array of these objects. A Structural Result Object MAY declare a named expression over the merge record (see §4.5.14). `mode` is reserved for implementation-defined behavior and MUST NOT change the core ordering. `items` MUST NOT be set on a `merge`.

- **`await`** — Evaluates its required `wait` predicate immediately, then repeats evaluation after the executor's configured polling interval (200 ms by default) until it is truthy. On truth, nested `steps` execute once. An evaluation error fails the construct. A serialized `timeout` bounds the whole await; otherwise an executor-owned default MAY do so. Expiry fails the construct; context cancellation terminates it. `cases`, `default`, and `items` MUST NOT be set on an `await`.

The constraints above apply identically to any Step Object that sets `type`. The canonical `versions/1.11.0.json` schema encodes them as a shared compound (`$defs/structural-type-constraints`) and applies it to workflows unconditionally and to steps via `if: { required: ["type"] }`.

##### 4.5.6.4 Workflow Timeout

`timeout` bounds the structural workflow and all descendant work started by that workflow. The timeout clock starts when the workflow is eligible to start, after its `dependsOn` dependencies have completed and after its `when` condition allows execution.

When a workflow timeout expires, the workflow fails and the executor SHOULD cancel descendant work that was started by the workflow. A parent context cancellation MAY terminate the workflow before its timeout expires.

##### 4.5.6.5 Workflow Idempotency

`idempotency` applies to one logical execution of the workflow. It does not apply to every operation automatically and does not replace explicit API-level idempotency request bindings.

The executor resolves the idempotency `key` when the workflow is eligible to start. The idempotency identity is `(document identity, workflowId, resolved key)`. The executor MUST reserve the idempotency identity before starting side-effectful work in the workflow.

If no prior record exists, execution proceeds and the executor records the terminal outcome. If a prior record exists and `onConflict` is `reject`, the executor MUST fail before starting new side-effectful work. If a prior successful record exists and `onConflict` is `returnPrevious`, the executor MUST return the prior workflow outputs without starting new side-effectful work. If `onConflict` is `returnPrevious` but the prior record is not successful or retained outputs are unavailable, the executor MUST fail before starting new side-effectful work.

### 4.6 Validation

Core validation MUST check:

- `uws`, `info`, and `operations` are present.
- Version strings match the UWS 1.x lexical pattern and identify an exactly published core version. The lexical pattern is not an admission list. Validation and execution MUST reject prerelease, unpublished patch/minor, future, or otherwise unsupported versions; an older or latest schema MUST NOT be used as a fallback. The exact-version admission correction applies across all declared versions and does not apply later feature semantics retroactively.
- Source description names, operation IDs, workflow IDs, step IDs, trigger IDs, and parallel groups are unique where applicable.
- Trigger output labels are unique within each trigger.
- Workflow IDs and step IDs match `^[A-Za-z0-9_-]+$` so `StructuralResult.from` remains unambiguous.
- Source description types are `openapi`, `google-discovery`, `aws-smithy`, `asyncapi`, `graphql`, `openrpc`, `grpc-protobuf`, `odata`, or `browser-profile`; missing `type` defaults to `openapi`.
- Each source-bound operation references an existing source description.
- Each source-bound operation sets exactly one valid selector: generic `sourceOperationId` / `sourceOperationRef`, or legacy `openapiOperationId` / `openapiOperationRef` for `openapi` sources only.
- `google-discovery`, `aws-smithy`, `asyncapi`, `graphql`, `openrpc`, `grpc-protobuf`, `odata`, and `browser-profile` source-bound operations use generic selectors and reject legacy OpenAPI selectors.
- Each extension-owned operation includes `x-uws-operation-profile` with at least one non-whitespace character.
- In UWS 1.10 and later, expression-addressable output, document/component variable, workflow-input, and step-input names match `^[A-Za-z0-9_-]+$`; nested JSON object property names are not restricted by this rule.
- Dependency, operation, workflow, step, trigger route, success action, and failure action references resolve.
- Structural workflow and step types are known.
- A step that references an operation or workflow does not also declare structural child blocks (`steps`, `cases`, or `default`).
- Operation, workflow, and step `timeout` values are greater than `0` when present.
- Workflow `idempotency.key` is present and non-empty when `idempotency` is set.
- Workflow `idempotency.onConflict`, when present, is `reject` or `returnPrevious`.
- Workflow `idempotency.ttl`, when present, is greater than `0`.
- Version-gated fields and semantics are rejected or not applied on documents whose `uws` value predates their defining release. After exact-version admission, minimum-version gates use SemVer precedence; prerelease declarations are not supported. Unless a release explicitly declares a version-specific behavior, a later published stable release includes earlier minimum-gated features. The gates are: operation/workflow/step `timeout` and workflow `idempotency` in 1.1; generic selectors and Google Discovery/AWS Smithy source types in 1.2; AsyncAPI in 1.3; GraphQL, OpenRPC, gRPC/Protocol Buffers, and OData in 1.4; Browser Profile in 1.5; `ansible-module` in 1.6 (removed in 1.7.0); Browser Capability Profile 1.6 and Browser Authentication/Call 1.1 in 1.8; Browser Capability Profile 1.7 and `contentTrust` in 1.9.0 and 1.9.1 respectively; compatible content-trust and validation corrections in 1.9.2; portable expression/evaluation/execution semantics in 1.10.0; and response-body dot-walk, `$batchIndex`, numeric non-`await` `wait`/`batchSize` literals, root-scoped terminal `goto`, and revised `forEach` merge selection in 1.11.0. Browser profile versions 1.7 through 1.9 remain separate profiles and specify their own UWS minimum; they do not add core source types. A Go validator MUST report the matching `requires UWS 1.x.0 or later` error for versioned fields used before their defining minor version, and MUST reject `ansible-module` on documents declaring 1.7.0 or later. Profile-aware tooling validates the separate profile discriminator.
- `contentTrust` is rejected before UWS 1.9.1. Its maps reference declared identifiers, per-output and per-input keys reference existing operation outputs and workflow input properties, every level is `unknown`, `trusted`, or `untrusted`, and empty no-op declaration objects are invalid.
- Structural construct field constraints hold (see §4.5.6.3): `loop` requires `items`; `await` requires `wait`; `switch`, `sequence`, `parallel`, `merge`, and `await` MUST NOT set `items`; `loop` and `await` MUST NOT set `cases` or `default`.
- Each `StructuralResult` resolves `from` to a known workflow or `workflowId.stepId` pair whose `type` is structural and matches the result `kind` (see §4.5.14).
- Each trigger route `output` references a declared entry in the parent trigger's `outputs` list (see §4.5.9).
- Each trigger route `to` item references either a declared `workflowId` or a top-level `stepId` in the document's executable entry workflow (see §7.8).
- In UWS 1.10 and later, executable identifiers are unambiguous across operation IDs, workflow IDs, step IDs, and parallel-group IDs. A parallel-group ID may be shared by its members; a step ID may equal its directly referenced operation ID. Document execution selects the sole workflow, or requires exactly one `main` when multiple workflows are declared. Explicit operation/workflow/step execution does not require a document entry. Workflow-reference `workflow` values are literal IDs.
- `x-*` fields are preserved as specification extensions.

Schema validation checks document shape. Semantic checks such as exact published-version admission, duplicate identifiers, source type / selector compatibility, and reference integrity are enforced by the Go `Validate` and `ValidateResult` APIs. Identifier uniqueness is semantic: two array entries with the same identifier but different payloads are not rejected by JSON Schema `uniqueItems`, and UWS 1.11 does not use `uniqueItems` on identifier-bearing top-level arrays for that purpose.

Content-trust findings are not validation errors. Once a `contentTrust` declaration passes the structural and semantic rules above, advisory analysis is invoked explicitly as described in §4.7.

### 4.7 Advisory Content-Trust Analysis

UWS 1.9.1 introduced deterministic advisory analysis over the normative runtime-expression grammar, and UWS 1.9.2 supplies the compatible refinements in this section. The Go entry point is:

```go
func Analyze(ctx context.Context, doc *uws1.Document, resolvers ...Resolver) (*Report, error)
```

The report contains ordered data-flow edges and findings. It MUST NOT include runtime values, content excerpts, resolver error details, credentials, or secrets. Findings do not enter `ValidationResult`, prevent execution, alter orchestration, or change executor results.

Core operation, workflow, and step flow is statically recoverable. An operation resolver describes RFC 6901-relative input channels as `data`, `instruction`, or `authority`, output value contracts, resolver-provided default provenance, and whether derived output inherits input provenance. Array-index tokens in resolver pointers use canonical decimal form: `0` or a non-zero digit followed by digits. A resolver MAY supply references extracted from an implementation-specific interpolation language. Without those references, the analyzer scans the declared channel subtree for exact UWS expressions. If a resolver claims an operation but declares no input channels, the analyzer scans the core request tree rather than treating the request as implicitly trusted. An implementation-specific or ambiguous expression remains opaque. If more than one resolver claims an operation, the analyzer reports a conflict rather than selecting one.

#### 4.7.1 Provenance

Operation output provenance uses this precedence:

1. the per-output operation declaration;
2. the operation declaration's `default`;
3. the bound source-description declaration;
4. the resolver-provided default;
5. `unknown`.

Trigger payloads default to `untrusted`. Where routes identify the reachable workflow or top-level step, analysis joins only the trigger declarations that can reach that scope; a trigger elsewhere in the document does not taint an unrelated route. Reachability MUST use execution's namespace rules: route targets prefer workflows over top-level steps, generic dependencies prefer steps over workflows over operations, and `operationRef` and `workflow` are typed references. External workflow-entry inputs default to `unknown`. Document literals, `variables`, and `components.variables` are `trusted` only under the assumption that the document itself has been reviewed. Same-document workflow calls propagate the computed provenance of their bound inputs and MUST NOT use an entry-input declaration to launder them.

Untrusted values remain untrusted through derivation. A per-output declaration classifies the operation-produced value but MUST NOT upgrade provenance inherited through a same-scope alias or another expression reference. An LLM `data` input is permitted and may taint derived model output. An untrusted `instruction` input or a later use in an `authority` channel is reported.

#### 4.7.2 Value Capability

Analysis tracks value capability separately from provenance. The capability is one of `free_text`, `constrained_scalar`, `composite`, or `unknown`. Boolean, numeric, and enum narrowing removes free-text injection capability but does not change `untrusted` provenance. A constrained attacker-controlled value can still influence control flow or an authority-bearing input.

#### 4.7.3 Control Flow and References

The analyzer accounts for declaration order in `sequence`, explicit dependencies, structural entry and exit, switch branches, loops, nested structural-result targets, and same-document workflow calls. An earlier sequence step establishes happens-before without requiring `dependsOn`. An unconditional child dominates its structural container's output evaluation only when that structural type executes the child; `merge` consumes dependency records and does not execute nested steps. A workflow-level `when` or `forEach` gates the workflow as a whole and does not make its unconditional steps non-dominating at that workflow's exit. A reference whose producer does not dominate its use is reported. Branch-only and possibly-empty loop producers do not dominate uses outside those constructs.

Same-scope `$outputs` aliases are evaluated in lexical output-name order, matching core execution. An alias can consume only a same-scope output already resolved in that order; a forward alias is unresolved. Provenance propagation continues to an actual fixed point before the report is emitted; document size is not used as a heuristic iteration limit.

The stable finding codes are:

- `content_trust.untrusted_instruction` and `content_trust.untrusted_authority` (high severity);
- `content_trust.untrusted_control`, `content_trust.unknown_provenance`, `content_trust.opaque_expression`, `content_trust.unresolved_reference`, `content_trust.non_dominating_reference`, `content_trust.resolver_failure`, and `content_trust.resolver_conflict` (warning severity).

Content-trust findings remain advisory through UWS 1.11. Later compatible patches may refine analysis only from implementation evidence; incompatible defaults, mandatory enforcement, or wire restructuring require a new major version.

## 5. Runtime Expressions

UWS uses runtime expression strings in control-flow fields (`when`, `forEach`, `wait`, `items`, `batchSize`), workflow idempotency keys, criterion conditions, structural-result `value` fields, the string values of `outputs` maps, the values of a step's `inputs` map (§4.5.7), and `request` binding values (§4.5.5) whose resolved values are bound before the operation is dispatched. The `workflow` step field is a literal workflow ID, not an expression. A runtime expression is a string whose resolved value is a JSON-compatible value determined at execution time. Whether a given request-binding or input value is a literal or an expression is determined by the runtime that resolves it; UWS core does not statically distinguish the two. Resolution of an expression's target (for example, the existence of a referenced `$steps.<stepId>` output or `$inputs.<name>` binding) is the responsibility of the bound runtime and is not enforced by UWS core schema or semantic validation.

Conforming implementations MUST accept the expression sources defined in §5.1, the JSON Pointer fragment form in §5.2, the output dot-walk in §5.3, and the comparison operators in §5.4. Implementations MAY support additional syntax as described in §5.5.

### 5.1 Expression Sources

Expression strings reference data through these normative sources. Each source begins with a leading `$` sigil. A dotted suffix `.<path>` is a sequence of one or more dot-separated segments, where each segment matches `id-char` (`[A-Za-z0-9_-]`) and is resolved against the current value as an object property name or array index.

| Source | Meaning |
|---|---|
| `$response.statusCode` | HTTP response status code of the current operation. |
| `$response.body` | HTTP response body of the current operation. |
| `$response.body<json-pointer>` | A JSON Pointer fragment (§5.2) into the response body. |
| `$response.body.<path>` | From UWS 1.11, dot-walk into the response body using the same segment rules as §5.3. |
| `$response.headers.<name>` | HTTP response header value by name. |
| `$outputs.<name>` | Same-scope output value declared by the enclosing operation, workflow, or step. |
| `$outputs.<name>.<path>` | Dot-walk into a structured output value (see §5.3). |
| `$steps.<stepId>.outputs.<name>` | Output of a named sibling step within the same workflow. |
| `$steps.<stepId>.outputs.<name>.<path>` | Dot-walk into a named sibling step's output value. |
| `$variables.<name>` | A document-scope variable declared under `variables` or `components.variables`. If both declare the same name, top-level `variables` takes precedence. |
| `$variables.<name>.<path>` | Dot-walk into a structured variable value. |
| `$trigger` | The input payload delivered by the enclosing trigger. Trigger identity and output metadata are not part of this expression value. |
| `$trigger.<path>` | Dot-walk into the trigger payload. |
| `$item` | The current iteration value. Valid only inside a `forEach` context (operation, workflow, or step). The value is the element at the current index of the resolved items collection. |
| `$index` | The 0-based integer index of the current iteration. Valid only inside a `forEach` context. |
| `$batchIndex` | From UWS 1.11, the 0-based integer index of the current sequential batch. Valid only inside a `loop` context. |
| `$inputs` | The current scope's input bindings. In a workflow step's `inputs` values: the enclosing workflow's runtime-provided inputs. In an operation's `request` fields: the calling step's `inputs` bindings. Because an operation MAY be referenced by more than one step, `$inputs` in an operation's `request` fields is resolved dynamically, per invocation, against the step that invoked the operation — not statically against a single binding set. |
| `$inputs.<path>` | Dot-walk into the current scope's inputs. |

A resolved value MAY be of any JSON type: string, number, boolean, null, object, or array.

HTTP response header lookup through `$response.headers.<name>` is case-insensitive, as required for HTTP field names. The spelling of the supplied `name` therefore MUST NOT affect which field is selected.

### 5.2 JSON Pointer Fragments

A JSON Pointer fragment `<json-pointer>` is an RFC 6901 JSON Pointer prefixed with `#`. It MAY be used as a suffix on `$response.body` and as the value of `Criterion.context` when `Criterion.type` is `jsonpath`. The pointer resolves against the value named by its prefix. When a token indexes an array, it MUST use canonical decimal form: `0` or a non-zero digit followed by digits. For `jsonpath` criteria, a condition beginning with `/` is also accepted as a direct pointer lookup form; it is interpreted as if prefixed with `#` and is not itself an RFC 6901 URI fragment.

Example:

```text
$response.body#/items/0/name
```

### 5.3 Output Values and Dot-Walk

Each entry in an `outputs` map of an operation, workflow, or step is a pair `<name>: <expression>`. The `<expression>` is a string that conforms to §5.1. At execution time, entries are evaluated in lexical output-name order and each resolved value is bound to `<name>` in the enclosing scope. A same-scope `$outputs.<name>` reference can therefore consume only an output already resolved in that order; forward references fail expression evaluation.

A resolved output value MAY be of any JSON type. Consumers MAY dot-walk into structured outputs, and from UWS 1.11 into `$response.body`:

- `$outputs.<name>` resolves to the whole bound value.
- `$outputs.<name>.<segment>` resolves to the result of applying `<segment>` as an object property name (for JSON objects) or a decimal array index (for JSON arrays).
- Subsequent segments apply recursively.

For `$response.body.<path>`, the same property/index lookup and missing-value rules apply to the response body. The initial response-body dot-walk form is available only in UWS 1.11 and later; a JSON Pointer fragment remains available in earlier versions.

If a segment does not resolve — the property is absent from a JSON object, the index is out of bounds on a JSON array, or the segment is applied to a scalar — the expression value is `null`.

The typed shape `Map[string, string]` in the UWS document model reflects the *expression* type, not the resolved runtime type.

### 5.4 Comparison Operators

Inside `when`, `Criterion.condition` when `Criterion.type` is `simple`, and any field documented as a boolean expression, conforming implementations MUST support the comparison operators `==`, `!=`, `<`, `<=`, `>`, and `>=`.

- Operands MUST be of the same JSON type. Implementations MUST NOT perform implicit type coercion.
- `==` and `!=` are defined for strings, numbers, booleans, and `null`.
- `<`, `<=`, `>`, and `>=` are defined for strings (lexicographic) and numbers. Applying an ordering operator to booleans, `null`, objects, or arrays is an error; implementations MUST treat the comparison as failing.

### 5.5 Implementation Extensions

Richer expression features — such as boolean connectives (`&&`, `||`, `!`), arithmetic, function calls (for example `length()`), or string operations — are implementation-defined. A conforming UWS core implementation MUST NOT require such features in order to parse documents that use only §5.1–§5.4 syntax. A UWS document that depends on features beyond §5.1–§5.4 is tied to the implementation profile that defines them and SHOULD declare that dependency via an `x-uws-operation-profile` or equivalent extension marker on the relevant operation.

### 5.6 Formal Grammar

The following ABNF (RFC 5234) defines the canonical parse for UWS runtime expression strings. This grammar is normative and authoritative; where §5.1's tabular description is less specific, the grammar here applies.

```abnf
; ===== UWS 1.x Runtime Expression Grammar (RFC 5234 ABNF) =====

expression     = condition / source-expr

condition      = source-expr SP op SP operand
operand        = source-expr / literal
op             = "==" / "!=" / "<=" / ">=" / "<" / ">"

source-expr    = response-expr
               / outputs-expr
               / steps-expr
               / variables-expr
               / trigger-expr
               / inputs-expr
               / item-expr
               / index-expr
               / batch-index-expr

response-expr  = "$response.statusCode"
               / "$response.headers." header-name
               / "$response.body" [ json-pointer / response-dot-path ]
response-dot-path = "." path ; available only in UWS 1.11 and later

outputs-expr   = "$outputs." name [ "." path ]
steps-expr     = "$steps." identifier ".outputs." name [ "." path ]
variables-expr = "$variables." name [ "." path ]
trigger-expr   = "$trigger" [ "." path ]
inputs-expr    = "$inputs" [ "." path ]
item-expr      = "$item" [ "." path ]
index-expr     = "$index"
batch-index-expr = "$batchIndex" ; available only in UWS 1.11+, inside a loop

wait-value       = source-expr / json-number
batch-size-value = source-expr / json-number
; A bare json-number is permitted only for non-await wait and batchSize in UWS 1.11+.
; await.wait remains a predicate expression. Earlier versions require an expression source.

path           = segment *( "." segment )
segment        = 1*id-char
name           = 1*id-char
identifier     = 1*id-char
header-name    = 1*( ALPHA / DIGIT / "-" / "_" )
id-char        = ALPHA / DIGIT / "_" / "-"

json-pointer   = "#" *( "/" token )
token          = *( unreserved / escaped )
unreserved     = ALPHA / DIGIT / "-" / "_" / "."
escaped        = "~0" / "~1" / pct-encoded
pct-encoded    = "%" HEXDIG HEXDIG

literal        = json-string / json-number / json-bool / json-null
json-string    = DQUOTE *json-char DQUOTE
json-char      = unescaped-char / escape-seq
unescaped-char = %x20-21 / %x23-5B / %x5D-10FFFF
escape-seq     = "\" ( DQUOTE / "\" / "/" / "b" / "f" / "n" / "r" / "t"
               / "u" 4HEXDIG )
json-number    = [ "-" ] int [ frac ] [ exp ]
int            = "0" / ( %x31-39 *DIGIT )
frac           = "." 1*DIGIT
exp            = ( "e" / "E" ) [ "+" / "-" ] 1*DIGIT
json-bool      = "true" / "false"
json-null      = "null"

SP             = %x20
DQUOTE         = %x22
ALPHA          = %x41-5A / %x61-7A
DIGIT          = %x30-39
HEXDIG         = DIGIT / "A" / "B" / "C" / "D" / "E" / "F"
               / "a" / "b" / "c" / "d" / "e" / "f"
```

Interpretation notes, normative:

1. **Segment tokenization.** Path segments are dot-separated and MUST match `id-char` — that is, `^[A-Za-z0-9_-]+$`. From UWS 1.10, expression-addressable declaration names for outputs, document/component variables, workflow input properties, and step inputs MUST use this same character set. Earlier UWS versions retain their published name rules. Result names and trigger output labels are not expression-addressable declaration names and retain their own rules. A property name containing `.` in a runtime value can still be reached through JSON Pointer where that source permits it. The `$response.body.<path>` form and `$batchIndex` are new in UWS 1.11; `$batchIndex` is valid only in a structural `loop` context.

2. **Comparison operators.** The grammar covers a single binary comparison of the form `source-expr op operand`. Nested or parenthesised comparisons are not part of UWS core; an implementation that supports them does so under §5.5.

3. **Literals.** The `literal` production is the JSON grammar for string, number, boolean, and null values. A comparison operand that is not a `source-expr` MUST be a JSON literal.

4. **Whitespace.** A single SP (U+0020) surrounds `op` in a comparison. UWS core does not require implementations to accept additional whitespace.

5. **Operator longest-match.** `==`, `!=`, `<=`, and `>=` MUST be recognised as two-character tokens; `<` and `>` are the one-character alternatives only when the next character is not `=`.

6. **JSON Pointer escape.** Inside a `token`, `~0` represents a literal `~` and `~1` represents a literal `/`, per RFC 6901. A bare `~` is invalid; it MUST be followed by `0` or `1`.

### 5.7 UWS 1.10 and 1.11 Expression Evaluation

This section applies to documents declaring `uws` 1.10.0 or later. The response-body dot-walk, `$batchIndex`, and bare numeric `wait`/`batchSize` forms described in §5.6 apply only from UWS 1.11.0. Earlier versions retain their declared-version expression and criterion behavior.

- A truthy value is `true`, a nonzero finite number, a non-empty string, a non-empty array, or a non-empty object. `false`, numeric zero, the empty string, an empty array, an empty object, and `null` are false. Runtime values MUST be JSON-compatible; a non-finite number or unsupported value is an evaluation error.
- A criterion's `context` is evaluated first. All criteria in one list MUST match (logical AND); an empty list matches. Action lists are inspected in declaration order and the first matching action is selected.
- `simple` criteria apply the truthiness rule to their condition expression. `regex` criteria evaluate `context` to a string or UTF-8 byte sequence and use RE2-compatible regular-expression search semantics for `condition`. `jsonpath` criteria evaluate `context` to a JSON value; `condition` is a JSONPath query whose selected values are tested for truthiness, or a direct lookup when it begins with `#` or `/`. `xpath` criteria evaluate `context` to XML text and use an XPath 1.0 expression in `condition`; XPath Boolean conversion applies, and NaN converts to false. For all non-simple criteria, when `condition` begins with the exact `context` expression, implementations remove that matching prefix before interpreting the remainder as the regex, JSONPath/pointer, or XPath target. This permits a context-qualified target as well as a target relative to the evaluated context. An empty JSONPath target tests the context value's truthiness; an empty XPath target tests whether the context text is truthy. Missing pointers do not match; a present `null` value is found but false. Pointer fragments percent-decode before token splitting, accept only `~0` and `~1` escapes, and use canonical decimal array indexes.
- Expression-addressable declaration names MUST match `^[A-Za-z0-9_-]+$`. This applies to operation/workflow/step outputs, top-level and component variables, workflow input properties, and step input bindings. Names containing `.` remain permitted by earlier versions but cannot be addressed unambiguously by the UWS expression grammar.
- When top-level `variables` and `components.variables` declare the same name, the top-level declaration wins. `$steps` resolves records from the current workflow invocation only; nested or separate invocations are not implicitly visible. `$trigger` evaluates to the payload only. HTTP runtimes expose `$response.statusCode`, `$response.headers`, and `$response.body`; a non-HTTP runtime defines its `$response` shape in its operation profile.

## 6. Specification Extensions

Specification extensions are fields whose names begin with `x-`.

UWS core does not define service types for local commands, functions, file I/O, SSH, SMTP, SQL, object storage, LLM calls, browser automation, or other non-source behavior. These capabilities can be described through `x-*` extension profiles.

Example non-normative extension:

```json
{
  "operationId": "build_email",
  "x-uws-operation-profile": "acme-mail",
  "x-acme-runtime": {
    "type": "function",
    "function": "mail_raw",
    "args": {
      "subject": "Daily weather report"
    }
  }
}
```

The core specification preserves extension fields but does not validate or execute implementation-specific extension payloads.

### 6.1 Reserved Extension Prefixes

The following extension prefixes are reserved for the UWS specification and its governance. Third-party tooling MUST NOT introduce extension fields whose names begin with these prefixes.

| Prefix / field | Reserved for and current disposition |
|---|---|
| `x-uws-` | UWS-owned fields and supplements. Third parties MUST NOT introduce fields with this prefix. |
| `x-uws-operation-profile` | UWS core (§4.5.4.1): identifies the implementation profile for an extension-owned operation. |
| `x-uws-runtime` | Runtime Supplement 1.0: optional typed non-HTTP runtime payload. |
| `x-uws-browser-authentication`, `x-uws-browser-session` | Introduced by Browser Authentication Call Supplement 1.0 and retained by 1.1: reviewed authentication and session inputs. The current call supplement is 1.1; both artifacts remain separately versioned. |
| `x-uws-browser-registration` | Introduced by Browser Registration Call Supplement 1.0 and retained by 1.1/1.2: typed private registration inputs and reviewed checkpoints. The current call supplement is 1.2; each artifact remains separately versioned. |
| `x-uws-ansible-module` | Historical withdrawn Ansible Module Call Supplement 1.0 / UWS 1.6 material only. UWS 1.7 and later do not support the `ansible-module` source type. |

`x-uws-runtime-config` is not a standardized public field and is not defined by this registry. The list above identifies published names known to this specification; future UWS or profile supplements MAY add names and define their semantics. The prefix reservation itself applies to all `x-uws-*` names, including names not listed here.

Implementation profiles, runtimes, and vendor-specific tooling SHOULD adopt their own unambiguous prefix, for example `x-acme-`, `x-<vendor>-`, or `x-<product>-`. An extension whose prefix is not reserved by UWS core is governed entirely by the implementation that defines it.

When two non-reserved extensions target the same object, the implementation profile named by `x-uws-operation-profile` (or its nearest enclosing equivalent) selects which extension is authoritative. UWS core does not arbitrate between conflicting third-party extensions.

Conforming tooling that encounters an unknown `x-*` field MUST preserve the field on round-trip serialization and MAY ignore the field at runtime. Tooling MUST NOT silently drop, rename, or coerce an `x-*` field whose prefix is not understood.

## 7. Execution Model

The UWS Execution Model defines the normative behavior for orchestrating workflows and executing operations. UWS adopts a bound-runtime execution model: UWS core owns structural orchestration and execution-state transitions, while an implementation-specific runtime provides the concrete execution of leaf operations and the evaluation services required by runtime expressions and iterative constructs.

### 7.1 Bound Runtime and Execution Entry Points

Execution is defined only for a document, workflow, or step that has a concrete runtime bound by the implementation. Runtime binding is execution state, not serialized UWS document data.

Before document-level execution begins, an implementation MUST validate:

1. the document as a UWS document,
2. the document as executable under the current UWS execution rules, and
3. the document's executable entrypoint requirements.

Before workflow-level or step-level execution begins, an implementation MUST validate the document as a UWS document and as executable under the current UWS execution rules.

Before trigger dispatch begins, an implementation MUST validate the document as a UWS document and as executable under the current UWS execution rules. Trigger dispatch uses the document's bound runtime and does not define a separate trigger-local runtime contract.

### 7.2 Orchestrator-Owned Semantics

The Orchestrator is the authoritative UWS core component responsible for walking the executable graph, managing execution state, and applying the semantics of the six structural constructs defined in §4.5.6.3.

At minimum, the Orchestrator MUST own:

1. indexing of declared operations, workflows, workflow steps, top-level trigger targets, and `parallelGroup` membership,
2. dependency execution across operations, workflows, workflow steps, and `parallelGroup` barriers,
3. evaluation and enforcement of structural execution attributes such as `dependsOn`, `when`, `forEach`, `items`, `batchSize`, and `wait`,
4. execution of structural workflow types (`sequence`, `parallel`, `switch`, `merge`, `loop`, `await`),
5. processing of success and failure actions, including `retry`, `goto`, and `end`,
6. resolution of declared outputs and structural results, and
7. routed execution after trigger resolution.

Trigger ingress, hosting, transport, authentication, and persistence remain implementation-specific. Once a trigger event has been accepted for dispatch, UWS core owns route resolution and routed execution semantics.

### 7.3 Runtime Responsibilities

To execute a UWS document, an implementation-specific runtime MUST provide the following capabilities to UWS core:

1. **Leaf execution.** The runtime MUST be able to execute a single Operation Object (§4.5.4), whether source-bound or extension-owned.
2. **Expression evaluation.** The runtime MUST be able to evaluate UWS Runtime Expressions (§5) against the current execution context.
3. **Item resolution.** The runtime MUST be able to resolve the `items` or `forEach` expression used by iterative constructs into an ordered collection of items.

The runtime MAY additionally provide transport behavior, authentication handling, persistence, resumption, scheduling, worker allocation, and implementation-specific extension semantics. Those concerns are outside the serialized UWS wire format unless another specification or implementation profile defines them.

### 7.4 Execution Context

During orchestration, the implementation maintains execution context that is visible to runtime-expression evaluation and to runtime-owned leaf execution.

This execution context MAY expose:

1. a trigger context containing the active trigger identity, emitted output, output label, and payload,
2. an iteration context containing the active item, index, and batch information for iterative execution,
3. a current-execution context identifying the executable object currently being evaluated or run, and
4. the current input bindings visible as `$inputs`, and
5. a snapshot of execution records accumulated so far.

These runtime context objects are execution state. They are not serialized UWS core document fields and MUST NOT be confused with the inert portable page/frame topology declared by the separate Browser Capability Profile 1.9 and Browser Authentication 1.1 profile documents. Browser Registration 1.2 separately defines its reviewed human-verification contract; none of these profile contracts makes browser session handles core UWS fields.

### 7.5 Execution Records

An implementation MAY expose a snapshot of execution records after document execution, workflow execution, step execution, or trigger dispatch.

When execution records are exposed, each record SHOULD identify:

1. the executable object that produced the record,
2. the kind of executable object that ran,
3. the resulting status,
4. any implementation-provided result or output object, and
5. any implementation-provided error information.

The keying scheme used to address execution records is implementation-defined. UWS core does not standardize a serialized record store or a wire-format representation for execution history.

### 7.6 Trigger Dispatch

A trigger dispatch names one declared trigger, one emitted output, and one payload value.

For route resolution:

1. each `routes[].output` token is matched against the trigger's declared `outputs` list,
2. a route output token MAY identify an output by its label or by a zero-based decimal-string index into that list, and
3. a route that names an undeclared output is invalid.

Every matched route target in `routes[].to` MUST reference either:

1. a declared `workflowId`, or
2. a top-level `stepId` in the document's executable entry workflow.

Dispatch executes each routed target through the same orchestrator rules used for ordinary execution, including transitive `dependsOn` resolution, `parallelGroup` barrier handling, structural execution, and output propagation. When dispatch is active, the execution context exposes the trigger payload and emitted output through the trigger context described in §7.4.

### 7.7 Executor-Owned Options

An implementation MAY expose executor-owned execution options that affect runtime behavior without changing the UWS document itself.

From UWS 1.1, serialized `timeout` fields provide a portable timeout contract for operations, workflows, and steps. An implementation MAY also expose executor-owned defaults that apply when no serialized timeout is present. If an await timeout expires, expiry of that timeout MUST terminate the active await construct with an execution error. Independent of any timeout, context cancellation or equivalent implementation-defined cancellation MUST terminate the active await construct.

### 7.8 UWS 1.10 and 1.11 Portable Execution Semantics

The rules in this section apply to documents declaring `uws` 1.10.0 or later. Earlier documents retain their versioned behavior.

**Entry selection and identifiers.** `Document.Execute` selects the only declared workflow when exactly one exists. With more than one workflow, exactly one workflow MUST have the ID `main`; otherwise document-level execution fails before a workflow body runs. A document with no workflows has no document-level entry and cannot use `Document.Execute`. Direct operation, workflow, and step APIs run their named target rather than selecting the document entry, but executable validation still requires an unambiguous `main` when multiple workflows are declared. Executable IDs are globally unique across operations, workflows, steps, and parallel-group IDs, except a parallel-group ID may be shared by its members and a step ID may equal the ID of the operation it directly references. A `workflow` step field is a literal declared `workflowId`, not a runtime expression. Each nested workflow call has an invocation scope keyed by its caller step; nested step, operation, dependency, and merge records are isolated to that invocation. Recursive workflow calls fail.

An unqualified `dependsOn` name matching a parallel-group ID waits for that group's members as a barrier. Otherwise names resolve in this order: step ID, workflow ID, operation ID. Typed `operationRef` and `workflow` fields select their declared object kinds directly. A name collision that would make a reference ambiguous is invalid, except the directly referenced operation/step ID equivalence described above; in that exceptional case, an unqualified dependency resolves to the step.

**Delay and await.** A non-`await` `wait` field is a runtime expression evaluated once after dependencies complete and `when` passes, but before the executable body begins. It MUST resolve to a finite JSON number from 0 through 86,400 seconds inclusive. The orchestrator waits cancellably for that duration; fractional seconds are rounded to the nearest nanosecond. Evaluation failure, an invalid value, or cancellation fails before the body. A workflow/step delay is inside that construct's timeout. An operation delay occurs before its leaf attempt and does not consume the operation-attempt timeout. Non-`await` delays are not retried by an operation's `onFailure` actions. For `await`, `wait` remains a truthiness predicate: evaluate immediately, then poll at the executor's configured interval (200 ms default); execute nested steps once when true. Serialized timeout bounds the await; if absent, an executor-owned default MAY apply. Cancellation or timeout stops polling.

**`forEach` and structural results.** A resolved `forEach` collection is processed sequentially in source order. Each iteration binds `$item` and zero-based `$index`. On success, the parent execution record's result is an ordered array of per-item objects with `index`, `item`, `status`, `error`, `result`, and `outputs`; each declared output is also exposed on the parent record as an ordered array of per-iteration values. A `loop` result is an ordered array with `index`, `batchIndex`, and `item`; batches are sequential groups, not parallel scheduling. In UWS 1.11 and later, merge consumes only its declared dependencies and yields an ordered array of records with `id`, `kind`, `status`, `error`, `result`, and `outputs`, expanding parallel groups by member declaration order and repeated iteration records in numeric order. For a `forEach` dependency, iteration records replace the parent aggregate when at least one iteration record exists; otherwise the parent record is included once, including when the `forEach` was skipped or had zero items. A failed dependency aborts merge before records are collected. No other structural type synthesizes a result value. `results[]` remains a declaration of an expression over a structural construct; it does not prescribe a serialized execution-record store. Execution record key formats and persistence remain implementation-defined.

**Actions and operation outcomes.** A leaf runtime error or a false `successCriteria` result is an operation failure. When `successCriteria` is non-empty, every criterion MUST match for success; an empty list means no additional success condition. Failure and success action lists are evaluated in declaration order; all criteria within an action MUST match and an empty action-criteria list matches. The first matching action is applied. If no failure action matches, the operation error propagates. `retryLimit` counts retries after the initial attempt; each attempt gets a fresh operation timeout. A positive `retryAfter` is a cancellable delay before a retry. Errors while evaluating criteria fail the operation directly. After success, no matching `onSuccess` action means normal continuation. `end` stops the current top-level orchestration successfully. In UWS 1.11 and later, `goto` raises a terminal control transfer that unwinds the entire active top-level run, including a sub-workflow invocation, loop, or `forEach` item; remaining siblings and iterations do not run. The target step or workflow and its dependencies are invoked in root orchestration scope. Records in a caller-scoped workflow invocation do not count as root target records. A root target already in terminal `success`, `error`, or `skipped` status MUST fail explicitly; a root target that is still in flight MUST also fail rather than wait or replay. Otherwise the target runs once. After it completes normally, the top-level run ends without resuming at the caller or at siblings after the target. A control signal raised by the target is processed by the same root dispatcher. These control signals are not valid inside parallel branches.

**Trigger dispatch.** Dispatch selects a trigger by exact ID and an emitted output by zero-based index, which MUST be within the declared outputs. A route's output token matches either the declared label or its decimal index; when a token equals a declared label, label interpretation takes precedence. Matching routes and their targets are processed in declaration order. Repeated targets execute once per dispatch. Every target must be a declared workflow or a top-level step in the selected entry workflow. Missing triggers, invalid indexes, missing routes, and a valid output with no matching target are errors. Targets execute sequentially unless a target's own structural type introduces parallelism. Trigger ingress, authentication, transport and payload authorization remain the responsibility of the trigger host/runtime.

The executable language-neutral conformance corpus is `testdata/conformance/1.11.0.json`. It is UTF-8 JSON with top-level `uws` equal to `1.11.0` and a non-empty `cases` array. Each case has a unique non-empty `id`, an `operation`, and typed JSON `input` and `expected` values. A conformance adapter MUST recognize every operation it claims to run and MUST NOT silently treat an unknown operation as a passing case. The artifact is protected by SHA-256 `51ea40b3f392125a22a95d515ee5002071dd8f4d98ab49415819b62f61ef26b5`; the digest covers the exact file bytes, including whitespace and the final newline.

The defined operations are:

| Operation | Input | Expected |
|---|---|---|
| `expression.parse` | `declaredVersion`, grammar `field`, source `expression`, and Boolean `loopContext`; for `field: wait`, optional `constructType` identifies structural `await` | Boolean `valid`, indicating whether the expression is admitted for that declared version and context. Bare JSON numbers are accepted for `wait` only when `constructType` is not `await`, and for `batchSize`; an `await` wait remains a predicate. This checks grammar admission, not expression evaluation. |
| `document.validate` | `document`, a complete UWS document | Boolean `valid`; a vector MAY include `errorKind` to identify a portable failure category. |
| `document.execute` | `document`, a deterministic scripted `runtime`, and `observe` selectors | `errorKind`, ordered `leafOrder`, `recordStatuses`, `mergeResultIDs`, and `loopBatchIndexes`. A successful execution has `errorKind: null`. |

For `document.execute`, the scripted runtime's `items` object maps item-expression strings to JSON arrays; `expressions` maps expression strings to JSON values; and `leafFailures` maps operation IDs to the number of initial leaf attempts that fail before succeeding. The runtime resolves those exact mappings, evaluates `$item`, `$index`, and `$batchIndex` from the current iteration context, evaluates complete JSON-number literals as numbers, and records leaf operation IDs in call order. `observe.recordStatuses` is an ordered array of logical selectors. Each selector has `kind` (`step` or `workflow`) and `id`, and MAY include `workflowCallPath`, an ordered array of caller step IDs from the root to the invocation. `mergeResultIDsFrom` and `loopBatchIndexesFrom` each select a logical node in the same form. Selectors name UWS entities, not an implementation's execution-record keys. The expected `recordStatuses` array pairs each selector with its status (`success`, `error`, `skipped`, or `null` when no record exists); the remaining arrays report the selected portable result values.

`errorKind` values are labels for comparing vector outcomes, not a required public error API or exact error message. The current corpus uses `unsupported-version`, `goto-target-already-completed`, and `invalid-wait-duration`; adapters map their own diagnostics to these labels. Implementations SHOULD run every applicable vector in addition to validating documents against the exact-version schema. The corpus covers version-gated expression forms, exact-version rejection, and representative execution of numeric waits, `goto`, and `forEach` merge behavior; it is a conformance aid, not a substitute for the normative rules in this specification.

### 7.9 Conformance Classes

UWS conformance is language-neutral and separates document acceptance from execution:

1. **Schema conformance** validates document shape against the exact schema selected by `uws`.
2. **Semantic-validation conformance** enforces identifier, binding, reference, version-gating, and structural constraints that JSON Schema cannot express.
3. **Core-orchestrator conformance** implements portable dependency, control-flow, wait, action, trigger, iteration, merge, and expression-evaluation semantics defined by the declared UWS version.
4. **Runtime-integration conformance** supplies leaf execution, expression evaluation, and ordered item resolution while respecting the execution context and cancellation rules.
5. **Extension-profile conformance** is separate from core conformance and applies only when an implementation claims the named profile.

An implementation MAY conform to schema and semantic validation without executing documents. A runtime that claims UWS execution conformance MUST pass the schema, semantic-validation, and core-orchestrator requirements and MUST use a runtime satisfying the integration contract. Neither the Go API shape nor the implementation's execution-record key format is normative.

## 8. Security Considerations

UWS documents can contain request values, runtime expressions, trigger definitions, and implementation extensions. Tooling SHOULD treat documents from untrusted sources as untrusted input.

Before execution, tooling SHOULD validate documents against the exact declared-version schema, validate semantic references, and ensure every referenced source document is the intended, integrity-checked artifact. A runtime that loads source URLs SHOULD constrain schemes, hosts, redirects, private-network access, and response size to reduce server-side request forgery and resource-exhaustion risks. Trigger hosts SHOULD authenticate and authorize ingress before calling UWS dispatch; the core `authentication` string is descriptive metadata, not an authentication mechanism.

UWS core does not define credential storage. Credentials, provider defaults, and runtime-specific authentication metadata belong in implementation profiles or external secret stores. Implementations SHOULD avoid embedding secrets in UWS documents, expressions, outputs, execution records, or error messages, and SHOULD redact them from logs and reports.

Source-bound operation security requirements are derived from referenced source documents. UWS tooling SHOULD validate that referenced source descriptions are the intended documents before execution.

Implementations SHOULD impose execution budgets for expression evaluation, iteration count, concurrency, payload size, wait duration, total runtime, and retained records. Retry policies SHOULD be reviewed for side effects and replay safety; operation idempotency is not inferred from the presence of a retry action. Confidentiality controls and content integrity solve different problems. Secret-handling rules restrict sensitive data flowing outward; `contentTrust` describes reviewed provenance and capability, but is advisory only and does not sanitize, authorize, or block execution. Tooling SHOULD offer the deterministic UWS 1.9.1+ analyzer before execution while keeping policy decisions, including whether findings block a run, outside the core execution model. UWS does not prohibit model-backed or otherwise nondeterministic operations: the operation profile and execution environment SHOULD disclose material nondeterminism and behavior-affecting model/configuration so reviewers can assess repeatability and side effects. The concern is hidden behavior that cannot be reviewed, not a blanket requirement that every operation produce identical results. Security recommendations in this section do not assert that UWS core or a particular runtime implements these controls.
